# 开镜、命中与多人性能 · 2026-09-09

这一版修正了开枪方向被后续输入覆盖、准星与射线使用不同俯仰角，以及带镜步枪镜片遮挡视野的问题。人物运动仍影响精度；服务器继续判定弹药、射速、护甲、遮挡和伤害。

## 开镜与射击

旧版只记住“有人按过开火”，实际计算时却读取下一帧的转向、后坐力和开镜状态。AWP 自动退镜、快速转向或开枪后切刀，可能使这一枪使用腰射精度，甚至丢失。

现在每次实际开火都有独立编号，并保存当时的武器、方向和倍率。服务器在处理后续切枪前消费这份输入；编号去重、队列上限、150 毫秒过期时间及当前生命检查防止重复或过期执行。自动武器的射击间隔也不再逐次叠加服务器帧边界的延迟。

镜头与射线共用眼睛高度、俯仰角和圆形散布算法。站立、蹲伏、移动与空中精度参数读取本机安装的 CS2 `weapons.vdata`；原文件 SHA-256 为 `fbd0d6f754c234efb24ec5c6b8c335f190e67f17ac7ec98dc2cd2ea2ddb4037e`。速度惩罚改为连续变化，避免旧版跨过 0.8 米/秒就突然进入完整移动散布。精度恢复仍是网页实现，不能视为完整 Source 2 射击模拟。

## 移动目标与延迟

远端人物按快照时间插值，固定延后 80 毫秒显示。开枪会携带画面所用的目标时间，服务器在最多 200 毫秒内回溯人物位置。不会回溯生命值和护甲，也不会跨越重生、阵营改变或已死亡目标；地图遮挡保持服务器判定。

这能减少“瞄准看到的位置，服务器却用目标稍后位置判定”的偏差。它不是官方 sub-tick，也不能抵消超过回溯上限的延迟、丢包或客户端帧停顿。玩家碰撞体仍是网页几何近似，没有逐骨骼官方命中盒。

## 已实施的渲染优化

- 地图静态节点完成定位后固定矩阵，减少每帧重复计算。
- 第一人称补光缓存灯光引用，移除每帧两次全场景名称查找。旧版 CPU 采样中这一查找累计约占 9%；这不是整机帧率提升比例。
- 近处可见人物按最多 60 Hz 更新骨骼，远处可见人物 30 Hz，视野外人物 12 Hz；位置和朝向仍每帧插值。死亡、换枪及蹲伏变化立即处理。
- 增加客户端帧耗时、人物动画耗时、渲染提交耗时，以及服务器 tick 的有限窗口统计，便于区分本机渲染与服务器计算。

## 本次测量与升级判断

测量时间为 2026-09-09。公网主机采用独立低优先级进程做短时压测，没有把测试机器人加进真实玩家房间，也没有为压测重启在线游戏。

| 场景 | 实测 |
| --- | --- |
| 公网主机上的隔离房间，1 个真实 WebSocket 客户端 + 9 个机器人，30 秒 | 稳定后的单核 CPU 29.4%–36.5%，RSS 184–188 MiB |
| 同一场景的游戏逻辑 | tick p95 14.4–17.2 ms；预算 33.33 ms，调度间隔 p95 33.86–33.95 ms |
| 初始连接与预热 | tick p95 曾达 58.3 ms，开局存在短时峰值，不能只看平均占用 |
| 本机浏览器，最低画质、9 个机器人、1600×950、12 秒 CPU 采样 | 帧间隔 p50 11.2 ms、p95 16.9 ms；人物更新 p95 1.5 ms，渲染提交 p95 12.8 ms |

浏览器采样覆盖约 115 万三角形、409 次绘制调用，记录过 344 ms 单次长帧。CPU Profiler 本身会扰动帧时间；这不是“完全不卡”的结论，也不是用户实际游玩时的测试结果。当前与旧版采样的相机和人数不同，不能据此宣称固定百分比的帧率提升。渲染提交时间也不是 GPU 计时器读数。

**单间满员机器人房间的证据暂不要求升级服务器。** 多房间同时满载仍需另测；当前游戏逻辑主要运行在一个 Node.js 线程，加更多低频核心不会自动分摊每个房间。若真实负载下 tick p95 持续超过 33.33 ms，应先检查机器人导航与碰撞热点，再考虑更强单核或把房间分配到多个进程。若服务器 tick 正常而客户端渲染耗时上升，优先继续做人物材质合批、细节级别和可见性优化，增加服务器内存不会解决浏览器绘制开销。
